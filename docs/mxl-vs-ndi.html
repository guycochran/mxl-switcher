MXL vs NDI — the same source, measured side by side

The case for a shared-memory media layer is usually argued in the abstract: "zero-copy," "no decode." Here it is in numbers. We took one live Zoom participant and delivered it into a switching core two ways at once — native MXL and NDI — and measured both paths on the same machine, at the same time, at 1080p30. Everything below was measured, not guessed.

By Guy Cochran · Office Hours GlobalOct 2026 · ZoomISO, 1920×1080p30Companion: the common-read-window deep-dive

1Why this comparison is fair

Transport comparisons are usually apples-to-oranges — different sources, different machines, different scenes. This one isn't. The same ZoomISO Cloud instance published the same participant simultaneously as a native MXL flow (output 1) and as NDI (output 2), both consumed on the same box. The only variable is the transport and what each requires downstream. That makes the CPU delta a clean measurement of the transport's real cost, not an artifact of the test rig.

The distinction that matters: native MXL delivers V210 grains directly into shared memory — the consumer reads them with no decode and no colorspace conversion. NDI delivers a compressed stream that must be decoded and converted to the working format before a switcher can touch it. That decode/convert stage is not free, and this is a measurement of exactly how not-free it is.

2The result: MXL used ~2.18× less CPU

The complete NDI path used about 2.18× the CPU of native MXL to deliver the same participant at 1080p30 — roughly two additional CPU cores of work. Two things drive the gap. First, NDI delivery made ZoomISO itself work harder on the encode side. Second, and larger, the NDI path added a separate decode/convert ingress stage (127–170% CPU) that native MXL simply does not have — there is nothing to decode when the grains are already V210 in shared memory.

3And MXL preserved better motion

The CPU win did not come at the cost of quality — the opposite. We measured not just grain rate but unique picture rate (distinct frames per second, by content, not by plumbing — see why rate alone lies). Both paths reported zero transport drops, but the content told a sharper story:

  • MXL-only: zero drops, no degradation, a tight 29.0–30.3 unique fps — essentially every frame distinct, as live video should be.
  • NDI-only: zero transport drops, but 14.7–30.0 unique fps with intermittent repeated frames — the content occasionally stalled even though the pipe never reported a loss.

That NDI spread is exactly the trap the measurement doctrine warns about: a path can report "no drops" while the picture repeats. MXL's direct-to-shared-memory delivery kept the motion continuous; the NDI decode/convert stage introduced intermittent repeats under the same load.

4Where the CPU actually went

Breaking the two paths into their stages shows the decode/convert stage is the whole difference:

  • MXL ZoomISO CPU: 147–198% (encode to V210 shared memory)
  • NDI ZoomISO CPU: 172–236% (encode to NDI — already more than the MXL encode)
  • NDI decode/convert ingress: an additional 127–170% — the stage MXL doesn't need at all

Neither path showed monitor errors, restarts, or material memory growth over the runs. The switching core itself stayed cheap on both paths — tens of percent of one CPU and well under 100 MiB of RAM — because the core never decodes pixels regardless of transport. The cost lives entirely in getting the picture into the working format, and that is precisely the cost MXL removes.

5Method, briefly

A first simultaneous 10-minute run (both paths live at once) established the shape: both at 1920×1080p30, zero probe drops, zero restarts; MXL at 29.7–30.3 grains/sec and 24.3–30.3 unique fps; the NDI return at 29.0–31.0 grains/sec but 17.3–30.3 unique fps with intermittent repeats; the core at 39–61% CPU and 77–78 MiB. Twelve isolated late reads occurred across both sources and the core recovered from each continuously — no timeouts, reader reopenings, regressions, common-window failures, or active alarms.

We then ran controlled MXL-only and NDI-only passes to isolate ZoomISO's encoding cost from the downstream NDI decoding cost — the numbers in the table above. The launcher was also fixed to automatically rediscover ZoomISO's regenerated MXL flow UUID after a protocol change, so the comparison is repeatable rather than hand-wired to one session's identifiers.

6The takeaway

NDI is an excellent, ubiquitous transport, and this is not an argument against it between devices or across a facility. It is a measurement of one specific thing: when a software media function needs a source in its working format, delivering it as native MXL V210 in shared memory avoids the decode/convert stage entirely — here, about 2.18× less CPU and better motion preservation for the same source at 1080p30. That is the Dynamic Media Facility thesis in one table: between software functions on a host, a shared-memory layer is the cheap path, and the savings are roughly two cores per source that you get back for more sources, more outputs, or smaller hardware.

For anyone deciding how to bring remote contribution into a software switcher: if the producer can emit native MXL — as ZoomISO Cloud now can — that is measurably the cheaper and cleaner way in.
