MXL vs NDI CPU — measured, reproducible, and bounded

The useful question is not “Which protocol wins everywhere?” It is narrower: what does each path cost when a same-host software switcher needs 1920×1080p30 v210? We measured that twice — first with a real ZoomISO participant, then with a deterministic moving source and controlled fan-out. The result is strong, and so are its boundaries.

By Guy Cochran · Office Hours GlobalOct 2026 · CPU-only dual-Xeon host · 1920×1080p30Runnable harness included

1The claim we can defend

For media functions co-located on one host, native MXL avoids the encode, network, decode, colorspace-conversion, and re-publication boundary needed to turn an NDI signal back into the switcher's v210 working format. In our live ZoomISO path, the complete NDI route used 2.18× as much CPU as native MXL. Put the other way, MXL reduced measured CPU by about 54%.

This does not mean “MXL replaces NDI.” NDI remains a practical device and network edge. The measured win is inside the software plant, where compressing pixels just to move them between processes on the same machine is avoidable work.

The isolated MXL pass averaged 165.74% CPU across 27 samples. The isolated NDI pass averaged 212.65% in ZoomISO plus 148.35% in the decode/convert/MXL bridge across 25 samples: 361.00% total. In Docker's accounting, 100% is one logical CPU, so the observed delta was about 1.95 CPU cores per 1080p30 source.

Both passes ran for five minutes with zero monitor errors and zero probe drops. The same source and host were used, but the passes were sequential rather than simultaneous; source motion and background scheduling were therefore not bit-identical. That is why the CPU result is the headline and the earlier unique-picture observations are treated as operational observations, not proof that one transport has better picture quality.

3Deterministic fan-out: same pixels, complete usable paths

A second test removes participant motion from the equation. Sixty moving 1920×1080p30 v210 frames are generated once, outside the measurements, then replayed in every phase. The MXL path writes them to an isolated shared-memory domain. The NDI path converts those same v210 frames to UYVY, sends them as NDI High Bandwidth, receives and converts them back to v210, then publishes the result into the same kind of MXL domain the switcher consumes. One and two identical MXL readers are then attached.

Across the clean controlled gates, the complete NDI route used 1.78–2.14× as much median CPU, while native MXL reduced measured compute by 43.9–53.4%. CPU is summed across every required container at each timestamp: source and reader(s) for MXL; source, NDI receive/convert/MXL bridge, and the same reader count for NDI. The headline uses medians across 14–15 samples per phase because this shared host also carried the permanent demonstration stack. Means and p95s remain available in the public aggregate CSV.

Counting the entire usable route is intentional. Stopping the NDI measurement at a decoded UYVY discard sink would omit the conversion and publication required before this v210 switcher can use the signal. Conversely, downstream MXL reader cost is counted on both sides.

4Method and reproducibility

  • Host: one CPU-only, dual-socket older Xeon server; the same permanent background workload remained in place for every phase.
  • Media: sixty deterministic moving 1920×1080p30 v210 frames, generated once before sampling and replayed identically in each phase.
  • MXL path: source → mxlsink → 1/2 independent mxlsrc readers.
  • NDI path: source → v210-to-UYVY → NDI sender → NDI receiver → UYVY-to-v210 → mxlsink → the same 1/2 MXL readers.
  • Sampling: warm-up before each phase; CPU and RSS sampled only for exact benchmark containers with docker stats; reader frame rate and drops verified separately.
  • Isolation: unique temporary names and a unique RAM-backed MXL domain; exact cleanup after every phase; no production mappings or services changed.

The runnable harness is tools/benchmark_mxl_vs_ndi.sh. It emits the raw resource CSV, reader summaries, environment versions, logs, and exit status. The repository's public safety checks keep machine addresses, credentials, meeting data, and private evidence locations out of this page.

5Operational corroboration under a real mixed workload

A separate ten-minute run carried two native MXL participant sources and two NDI participant sources simultaneously into Core. All six observed flows — four inputs plus Program and Preview — held 30.00–30.01 fps with zero probe drops and no hard-counter movement. Each NDI-to-v210/MXL bridge consumed 1.66–2.20 CPU cores; the native MXL inputs required no equivalent bridge. Because those four sources carried different participant pictures, that run confirms operation and bridge cost, not codec image quality.

6What this proves — and what it does not

Supported by the evidenceNot supported by the evidence
Native MXL materially reduced CPU in this same-host v210 switcher path; the removed work is visible as a discrete NDI encode/decode/convert/re-publication boundary. That every NDI product, codec mode, GPU path, CPU generation, resolution, or network will show the same ratio.
On this older CPU-only host, the savings are large enough to return useful whole cores to composition, encoding, or additional sources. That MXL is the right inter-host transport, or that NDI is unnecessary at device and facility edges.
The harness is repeatable and publishes exact topology, versions, rates, drops, and per-process resource measurements. A causal picture-quality advantage; that needs matched captured frames and objective image analysis.

7Why the architecture predicts the result

The measurements line up with the designs. The MXL project describes zero-copy or low-copy shared media exchange and native v210 video. The EBU's MXL overview places that exchange between professional media functions. NDI's own documentation describes NDI High Bandwidth as a compressed SpeedHQ format, and its performance guidance explains that encoding and decoding use multiple CPU cores. Both are doing what they were built to do; the question is where each belongs.

8The takeaway

Use NDI where you need a flexible IP edge. Keep MXL between co-located software functions. In this switcher, crossing an NDI boundary and returning to v210 more than doubled the measured CPU for the live source path; native MXL kept those cores available for the show.
