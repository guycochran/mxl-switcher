Oct 2026MXL vs NDI — the same Zoom source, measured side by side

We delivered one live Zoom participant into a switching core two ways at once — native MXL and NDI — on the same machine, at 1080p30, and measured both. The complete NDI path used about 2.18× the CPU of native MXL for the same source — roughly two extra CPU cores — because NDI needs a decode/convert stage that shared-memory V210 simply doesn't. MXL also preserved better motion: a tight 29.0–30.3 unique fps versus NDI's 14.7–30.0 with intermittent repeated frames (zero transport drops either way — the repeats were content, not loss). Not an argument against NDI between devices; a clean measurement of the cost of getting a source into a software function's working format.

Oct 2026A live Zoom gallery, switched on an MXL-native core

We brought ZoomISO Cloud's native MXL output into a from-scratch, dependency-free switching core and ran four isolated Zoom participants as Program and Preview sources — direct cut, preview, and broadcast-style take, every command committed on a frame boundary. This is the Dynamic Media Facility promise made concrete: two independent media functions — a remote-contribution gateway and a switcher — exchanging V210 over MXL shared memory, composed by anyone. From a loaded 30-minute run:

  • Zero dropped grains. Four inputs plus Program and Preview held 30.00 fps with no drops for the full run; every timing and validity counter stayed at zero.
  • The switcher is nearly free. The core held the four-source cut/take path in under 80 MiB of RAM at a fraction of one CPU. The cost of software media lives in contribution and conform — not in the switch.
  • Interop, not a diagram. Most of the field shows architecture slides; this was two separate builds exchanging real flows, with measured results.

This is a candidate build on a validation branch, not the default — and the eight-hour acceptance gate is the next milestone before we'd call it more than a reference result. But a remote Zoom guest, cut to air on an open MXL-native core, is the interop slice we set out to prove.

Oct 2026When two MXL sources must not share an index

Switching four independent sources surfaced a subtle timing truth worth writing down. MXL flows are small rings — six grains here — and two independently-paced producers (say, two Zoom participants whose encoders adapt separately) can drift several frames apart. A switcher that insists both sources sit at one common index then watches that shared readable window collapse, and faults — even though every source is perfectly healthy. The failure looked mysterious; the cause was deterministic: a six-grain ring affords only four frames of cross-source drift tolerance.

The fix was conceptual, not brute force: a cut doesn't need a common index at all. Program reads its source and Preview reads its source, each at its own latest-safe grain; a shared window is required only during a transition that samples both sources into one output. Relaxing "common index" to "per-output index, reset cleanly on each cut" made the drift problem disappear for ordinary cuts — which are the overwhelming majority of a show. Transitions keep the common window, protected by a bounded wait, forward-only recovery, and hold-last-valid.

Oct 2026“Is it flowing” is not “is it good”

A monitoring lesson from running MXL under load: the obvious health metrics lie. Grain-rate, head-freshness, and “is the thumbnail updating” all read green through a frozen program — they measure motion of the plumbing, not change of the content. During the source-drift collapse above, the rate probes stayed perfectly green; only content-level checks told the truth.

  • Content-uniqueness at the domain. Hash a fixed centre slice of each grain and count distinct hashes per second. Real media carries sensor noise, so it stays near the frame rate; a repeat-delivery wedge collapses toward one. (Hash the centre — letterboxed and keyed frames have static top rows — and copy only the slice, never the whole 8 MB buffer.)
  • Byte-identical frames at the encoded output. YDIF == 0 is the only honest program-integrity signal: an encoder fed truly-repeated input emits exact-zero difference, while real video never does. Similarity metrics like mpdecimate false-fire on legitimately static shots — don't use them as freeze detectors.

Oct 2026The whole switcher, on one $400 box

We moved the entire facility off cloud VMs and onto a single second-hand dual-Xeon Supermicro bought for about $400 — and ran a live multi-camera show from it. Everything that used to need three cloud instances now fits in one commodity box: all source ingest, the shared-memory domain, the cut (input-selector), the H.264 encoder, WebRTC output, and the control plane. Four live, switchable sources at once — a test pattern, a Makito hardware encoder, a PTZ camera, and a phone streaming SRT over Wi-Fi — all cuttable from a browser. Notes from the build:

  • Commodity silicon is enough. MXL needs AVX2, not AVX-512 — so a cheap older Xeon runs the full stack. No GPU, no specialty NIC, no cloud bill.
  • Remote TD, anywhere. The control surface ("Skin") is served over a secure tunnel, so a technical director on any network can watch program and cut the show from a browser — the box stays behind the firewall.
  • Reboot-proof. A self-heal step brings the whole program chain back in the right order after a cold boot — wire the selector, cut to a live source, re-publish program, then verify it's actually advancing. Proven across repeated full reboots with zero hands on keyboard.

Oct 2026Correcting the record on EFA — it was the hardware, not the proxy

Earlier we reported that RDMA-over-EFA fabric transport failed in the cloud. The real cause turned out to be the instance type: our test ran on AWS Nitro v3 (no remote-write RDMA). Re-running on a Nitro v4 instance with EFA-direct, the RDMA target ran clean — no errors. The earlier "EFA failed" finding was an instance-type mismatch, not a bug in the proxy. The TCP fabric path remains the portable default; EFA is a real option on the right hardware.

Oct 2026AMWA publishes IN-001 — a control model for MXL

AMWA published IN-001, "API Requirements – Control of the Media eXchange Layer (MXL)" — the draft that starts defining how an external controller manages MXL readers and writers (MXL itself defines media exchange, not control). It's an open Increment soliciting public review. We wrote up what it is and mapped our own switcher's operations against it. Read it →

Oct 2026Revived from cold storage — and hardened

Brought the cloud switcher back up for a test session: two real cameras in a shared-memory fabric, a looping episode on playout, a live 2-up composite (camera + remote guest), WebRTC program and a real-time health dashboard — driven entirely from a terminal with nobody at the studio. Three things worth logging:

  • Host-to-host with mxl-fabrics-proxy. Swapped our hand-rolled fabric legs for Jonas Ohland's proxy — rkeys over HTTP, atomic reload, Prometheus metrics. Carried a live flow at a measured 30 grains/s. The proof →
  • An honest outage, diagnosed live. A decommissioned cloud endpoint silently broke every feed; root-caused and fixed on air. Operations credibility you can't fake.
  • Cold-boot resilience closed. The VM-side ingests are now systemd-persistent (verified against a simulated cold boot) — the facility now survives a full reboot untouched.
