Field findings

Running MXL as a real remote production

Notes from building a browser-native broadcast switcher on the Media eXchange Layer — September 2026, MXL SDK v1.1 era, stock ghcr.io/cbcrc images on Azure. Everything below was measured, not guessed, and offered back as feedback to the MXL / mxl-hands-on / easy-mxl projects.

By Guy Cochran · Office Hours GlobalMXL SDK v1.1 · Azure D8s_v5 → D32s_v5Source: FINDINGS.md

1Remote sources stutter when cut — and why

MXL grains are indexed by TAI timestamp, not queue order. A remote camera's grains arrive ~transport-latency late, so a naive gateway writes them at indices behind the locally-generated flows' heads. A reader that aligns multiple flows (the input selector reads near "now") then finds the remote flow's grain not yet written → TOO EARLY / EAGAIN → the slot stutters, while single-flow reads of the same camera are flawless.

The fix that worked

Re-publish the remote flow with its PTS shifted so its head aligns with the local flows — a "latency normalizer." Two generations: cam_relay.py (fixed offset, hard-codes transport delay) and cam_ingest.py (own RTSP ingest, offset locked from the first buffer, self-tuning with slow drift re-sync — the keeper).

Upstream suggestion: the selector could read at min(head) across its inputs, or accept a per-slot read offset.

2Don't stamp arrival time into grain indices

The first version of cam_ingest.py stamped each buffer at arrival time. Under motion (camera pans), encoder bitrate spikes and network jitter grows; arrival jitter quantized directly into grain indices produces doubled/skipped grains — visible stutter exactly when the camera moves. Keep the stream's own regular PTS cadence and add one constant offset. Verified with a scripted VISCA pan + per-frame YDIF analysis: zero duplicate frames in motion after the fix.

3Robustness when grains are missing — measured

Flows are small rings (6 grains for 1080p30 video here). If a writer skips an index (or a reader races a write), the reader gets whatever is still in that ring slot — with a switcher upstream that can be a frame of the previous source. We recorded the program and caught two single-frame luma spikes (YAVG 38.8 → 58.6 → 38.8): one frame of test pattern flashing inside camera program.

Mitigation

Write the normalized flow ~2 grains ahead of "now" so aligned readers never race the writer. After the margin: 90 s / 2,685 frames, zero spikes. A reader-side "index was never committed" signal would let apps freeze-last-frame instead of showing stale content.

4The 2-second jitterbuffer hiding in uridecodebin

The stock HLS/RTSP gateway builds uridecodebin with defaults; for RTSP inputs that means rtspsrc latency=2000 — a silent 2 s of latency. Setting it in source-setup (150–200 ms works fine over SRT + LAN-quality links) removed almost all of our glass-to-glass latency. Result: the camera OSD clock and the cloud-keyed clock read the same second in a single program frame.

5mxlsink needs an explicit flow-id

An empty flow-id fails deep in negotiation as not-negotiated (-4) with the real error (Flow ID is invalid: invalid length: expected length 32) only visible at GST_DEBUG=mxlsink:5. Cost us a night of blaming caps. A fail-fast property check with a clear message would save others the same.

6Readers wedge when a source flow is recreated

Restarting any writer recreates its flow file; downstream readers (selector, keyer, encoder) keep stale handles and stall silently — status APIs still say running, no error surfaced. Recovery is a downstream cascade restart in dependency order. Upstream suggestions: readers could detect flow-file replacement and re-open; status APIs should report a stalled read. (This bug turned out to be a whole family — see §12.)

7Cross-host fabric: it works, and the receiving host is idle

We bridged the domain across VMs with the Fabrics API (TCP provider) and ran it as a three-node cluster (production VM → fabric peer VM → isolated "island" VM):

  • 30 grains/s sustained shipping the live 1080p30 v210 program (~1.3 Gbps), zero drops over 100k+ grains per leg, bidirectional legs concurrently.
  • Initiator ~10% of one core; target ~0% CPU — remote writes land in the destination ring without the receiving host's CPU in the data path.
  • Destination write-age 0.2–8 ms; with both hosts on NTP, the remote flow's head index equalled the local flows' heads — the stock input selector cut the fabric-delivered flow on air with no special handling.
  • libfabric ≥ 2.x is required (FI_SOCKADDR_IP): Ubuntu 24.04's packaged 1.17 — and even 1.22 — fail; we built 2.6.0 from the release tarball.
  • Non-routed networks: TargetInfo embeds the target's private bind sockaddr. Patching the address bytes ([4:8] of the base64 blob) to the target's public IP lets the initiator connect across unpeered VNets through cloud NAT at full rate — the exact recipe for cross-region or cross-cloud fabric.

Upstream suggestion: a supported "advertised address" field in TargetInfo would make NAT traversal first-class instead of a byte-patch.

Update · Oct 2026 — the proxy beats the hand-rolled legs

We later swapped our hand-built fabric legs for Jonas Ohland's mxl-fabrics-proxy and it's the keeper: it negotiates rkeys over HTTP (no more copying the target's JSON by hand), POST /v1/reload is atomic (retires the babysitter entirely), it exposes Prometheus /metrics + /healthz, and one Docker image ships its own libfabric (our hand-compiled 2.6.0 becomes irrelevant) with tcp | verbs | shm | efa selectable. Freshly measured proof: it carried a live camera flow host-to-host with mxl_grains_total climbing 411 → 501 in 3 seconds — exactly 30 grains/s, the camera's frame rate, and the flow materialized on the receiving host. Gotchas: the CLI's -s DOMAIN@mxl://… (an @, not =) is fiddly — use a YAML config; and the container must run --user 0:0 on a root-owned live domain (its worker mkdtemps inside the domain dir). The RDMA/EFA CPU-per-grain benchmark is the headline still to run. This is a clean example of standards over silos: a third-party proxy dropped straight onto our flows and carried live video with zero custom glue.

7.5The whole switcher, cross-cloud on AWS

§7 proved the fabric leg is cloud-portable. We then stood up the entire live switcher — not just the bridge — a second time, on a different cloud, fed by the real studio cameras. Two c5n.9xlarge instances in us-west-2, built straight from this repo (tools/*.py) plus the stock ghcr.io/cbcrc images and Jonas Ohland's mxl-fabrics-proxy, torn down after capture. The full signal path ran unmodified:

 Studio PTZ ───┐                      ┌─ Host A  c5n.9xlarge ────────────┐
 Makito X4 ────┤ cross-WAN SRT ─────► │ mediamtx ─ cam_ingest ─ SELECTOR │

               │                      │        ├─► mxl2webrtc (PGM out)   │
               │                      │        └─► mxl-fabrics-proxy ─────┼─► Host B

Every number reproduced the Azure fabric run almost exactly — the headline is that the whole switcher, not just the data plane, is cloud-portable; it behaves identically on Azure and AWS:

  • Both cameras 30.00 fps steady over cross-WAN SRT across the public internet (cam1 mapping error +19 ms, cam2 −9 ms).
  • Cross-host program over the fabric: 31.3 grains/s (line rate 29.97) at 3.99 ms p50 network latency — within rounding of the Azure run's ~30 grains/s / ~4 ms.
  • Live switching captured on program: a cut from cam1 (live PTZ) → a playout clip → cam2 (the Makito contribution feed) — the real selector cutting real sources in the cloud.
Honest caveat · the program shown is the clean selector output, not the keyed output

The HTML5 graphics keyer was bypassed this run: its headless-Chromium source errored on the first frame (GstCefSrc streaming stopped … reason error (-5)). This is not a GPU limitation — the same keyer runs fine on GPU-less Azure VMs. The likely cause (unconfirmed; the hosts were torn down before we debugged it) is that its lower-third.html polls a studio backend (prodbots.com/api/mxl/dip-state) that wasn't wired up on AWS, and/or the graphics server wasn't reachable at first-frame render. The networking mode was identical to Azure, so that's not it. Every production stage ran unmodified; the graphics overlay is one wiring fix away — point the graphic at a reachable or stubbed endpoint and pre-serve the page.

Honest caveat · the fabric leg is TCP; EFA/RDMA is one upstream fix away

This run bridged the two hosts over the proxy's TCP provider. The EFA/RDMA path on AWS is blocked by an upstream proxy bug (completion-queue setup, code -38), which we filed as jonasohland/mxl-fabrics-proxy#2. We make no EFA performance claims here — the RDMA path is identified, not yet measured. That the TCP latency (3.99 ms) already matches the Azure run is the point: the portability holds before RDMA even enters the picture.

8A broadcast contribution encoder as an MXL source

A static camera joins the selector without a studio-side re-encode hop: SDI camera → Haivision Makito X4 (1080i→1080p30, HEVC Main10, 20 Mbps) → SRT caller to the cloud VM's MediaMTX → GStreamer ingest → v210 flow → selector. Three lessons:

  • gst-libav defaults to slice threading in live pipelines. With a single-slice stream that means one core; HEVC 1080p30 10-bit missed realtime by ~30% on a loaded box. Fix: avdec_h265 thread-type=frame max-threads=4. After: 30.00 fps, mapping error under 60 ms over 10+ minutes.
  • Don't "fix" decoder threading encoder-side with multi-slice. 4 slices broke MediaMTX's H.265-in-TS framing. Keep slices=1 when MediaMTX is the SRT server.
  • 29.97 vs the domain's exact 30/1 grain rate is real: a videorate element re-times the stream, or caps negotiation fails outright against a 30/1 flow.
  • SRT latency is per-path, and too-tight is a silent killer. A camera running "behind the clock" (steady −68 ms offset, slow re-syncs) traced to the SRT push latency=20ms — fine for a 6 ms wired-studio hop, but 10× too tight for a 1080p60 camera whose 60 fps bursts overflow the window. Fix: raise to 200 ms. Rule of thumb: ~20 ms wired-LAN, ~200 ms studio→cloud, ~1000 ms cellular.
New · "slow switching" usually isn't the switcher

A perceived slow cut is almost never the selector — the API cut measured 65 ms and the backend forces a keyframe on every cut. The lag is the viewer's WebRTC/WHEP playout buffer (~0.5–1.5 s, normal). The lever is the encoder's key_int_max: 30 → 15 (a keyframe every 0.5 s) lets a viewer re-lock about 2× faster after a cut. Be honest in copy: this is "snappy, sub-second," not hardware-switcher-instant.

New · don't stack writers on a single-writer flow

Hand-launching ingests with docker exec -d can stack a second or third writer on the same single-writer MXL flow; readers then catch conflicting grains → the stutter/freeze/clock-jump family again. Distinct from the reader-lifecycle bugs (that's readers; this is writers). Fix: a bring-up that dedupes and guarantees exactly one writer per flow.

9The real cost of software media on a shared VM

Running the whole chain — CEF keyer, x264 WebRTC encoder, two camera decodes, plus a fabric leg — on one 8-vCPU VM ran it at ~13/8 load. Under visitor load the CEF keyer (software render, no GPU) lost its cores and its output flow froze the public program. Two fixes, no bigger box:

  • HEVC → H.264 for the contribution camera. Software HEVC decode cost ~1.3 cores; H.264 High costs ~0.5, invisible in 4:2:0-8-bit WebRTC output. When a software decoder is on the critical path, codec choice is a scheduling decision, not just a bitrate one.
  • Each mxlsrc SHM reader busy-spins a full core. The audio-follow-video writer held two of them and alone accounted for ~2 cores. A polling SHM reader is not free even when the media it carries is silence — account for readers, not just writers.

Result: load fell from ~13/8 to ~4/8; the freezes stopped.

10An MXL-native multiviewer: compose in the domain, encode once

A 3×3 production multiview built the way a hardware switcher does it — as a flow, not nine video players. One CPU compositor reads all seven switcher inputs plus the keyed program straight out of shared memory and writes the wall back to the domain as a new v210 flow; a single x264 leg encodes that one flow for every viewer. No GPU, and no source is ever decoded.

Cost: ~2 cores of a D32s_v5 at 15 fps, ~3.5 at 30 fps. We ran 30 for a day and went back to 15 — with the full chain beside it the box hit load 14/32 and the program encoder stuttered under thread contention during a live demo. A multiview is the first thing to de-rate when the program is the product. Note the recursion: compositor input #7 is itself a composited flow (the layout engine) — domain flows compose like any other source.

  • compositor ignore-inactive-pads=true EOS's instantly at startup — a latency= timeout handles absent sources correctly.
  • A live mpegtsmux in app code needs pipeline latency handling that gst-launch does for free: handle the latency bus message, keep an identity between mux and srtsink.
  • MediaMTX silently discards SRT payloads that aren't 1316-byte aligned. alignment=7 is mandatory; ffmpeg's default hides this, which is exactly why it's hard to spot.

11Assorted

  • CEF/HTML5 keyer on CPU tops out ~50 fps at 1080p (SwiftShader, no GPU on Azure D-series). Run at 1080p30 or use a GPU instance.
  • hls2mxl silently stops at VOD EOS (status still running); live RTSP input works well.
  • Selector defaults to 3 inputs — it's the container's MAX_INPUTS env, not a hard limit (we run 7).
  • Any NAT/cloud WebRTC deployment needs MTX_WEBRTCADDITIONALHOSTS=<public-ip> or viewers get only private ICE candidates (black video).
  • Prebuilt images assume AVX. On a QEMU VM with the default CPU model, every libmxl call SIGILLs (vxorps). Set the hypervisor CPU model to host.

12The reader-lifecycle bug is a family — the full taxonomy

§6 established that a reader wedges when its source flow is recreated. In a week of production it revealed five distinct species, each needing a different detector. This is the single most important thing we learned.

SpeciesWhat you seeWhat rate/head checks sayDetector that actually works

Repeat-delivery wedgefull 30 fps of the same grainall green — grains tick, head fresh, thumbs "update"unique-content count (md5 a slice)
Frozen-slices (+ stealth)target grains tick but slice payload stallsgrains/s = 30avg slices/grain decaying below 1080

The load-bearing insight

Rate, head-freshness, and thumbnail checks all read green through several of these species. The only honest detectors are content-uniqueness at the domain and byte-identical decoded-frame counting at the encoded output (see §14).

13The architectural fix: a flow stabilizer

Every mitigation in §12 is a bandage. The real fix is flow_stabilizer.py: a per-input relay that reads the volatile source flow and writes a stable flow that is created once and never recreated. When the volatile side churns, it swaps only its own reader in place — the sink and stable flow never stop, so every downstream consumer is permanently insulated.

  • Separate the output clock from the input. v1 passed input timestamps through; a stalled source made the stable flow jump. v-final drives output from a fixed 30 fps grid slewed to the wall clock and drops ahead-of-realtime arrivals — monotonic and real-time by construction.
  • The stabilizer process must be immortal. A supervisor respawn would recreate the stable flow — the exact failure it prevents. Any error swaps the reader instead of exiting.
  • Detect recreation by directory inode change, not by silence — an idle guest is silent legitimately; a recreated flow has a new inode.

Proven in isolation but not battle-tested under a live show (we rolled it back after iterating too aggressively mid-demo). It is the right post-v1.1.0 topology — deploy it from day one on a fresh build rather than retrofitting under fire.

14Measurement doctrine: rate metrics lie

If you take one operational lesson: "is it flowing" is not "is it good."

  • Grain rate, head freshness, thumbnail-updates all stay green through a repeat-delivery wedge. They measure motion of the plumbing, not change of the content.
  • Content uniqueness (hash a fixed slice of each grain; count distinct per second) catches repeat-wedges at the domain.
  • Byte-identical decoded frames (ffmpeg signalstats YDIF==0) is the only honest program-integrity signal — x264 emits skip-blocks for truly repeated input, while real video always carries sensor noise. Similarity metrics (mpdecimate) FALSE-FIRE on static scenes — we shipped that mistake and it needlessly restarted a healthy encoder.
  • Hash the CENTRE of the frame, not the top. Letterboxed 2-ups have static top rows; off-centre hashing reports false "frozen".

15Self-heal reflexes need a single arbiter

We accreted watchdogs under fire — repair cascade, guest-leg doctor, layout wedge-watch, fps-doctor, selector-doctor. Individually each is sound. Together, uncoordinated, they amplify. A stale guest branch once tripped a respawn storm — 38 repair events in 30 minutes, visible on program.

  • Fixes that worked: make warm-up manual-only (never ride a cascade); make take-check log-only; cap each reflex with per-branch strike files + cooldowns; and the rule — no cascade on a timer, only on a deliberate trigger.
  • The design lesson: past a handful of self-heal reflexes, they need one supervisor with a global action budget, not N independent loops. A cascade is a dice roll; fire it only when something knows the chain is broken.
New · a watchdog will fight a hands-off demo

The same babysitter that keeps an unattended facility alive actively broke a hands-off demo: its idle-reset read an un-clicked show as a dead one (after ~12 min idle it panned a camera home), and its repair-on-stale fired cascades every few minutes that churned the chain — the program pan went choppy and a 2-up layout kept flapping between sources, never settling. Nobody was doing anything to the show; the watchdog was doing it. The fix was to pause the watchdog for the duration of the demo (then re-enable it for unattended operation). Lesson: a persistence watchdog and a live demo want opposite things — give it a "demo mode" (or a much longer idle threshold) so "quiet" isn't mistaken for "broken."

New · your process counter is lying to you

While chasing the above we nearly misdiagnosed it as duplicate writers — because pgrep -cf cam_ingest.py reported two. It wasn't: pgrep -cf matches its own sh -c pgrep … command line, inflating every count by one. Use pgrep -af name | grep -v pgrep to actually count a pipeline's processes. A debugging tool that lies sends you fixing a problem you don't have.

16Operational recipes (the runbook)

  • mediamtx wedges silently — accepts SRT publishes but stops serving readers. Recipe: docker restart mediamtx + re-publish.
  • A "slow but flowing" fabric leg (4.3 grains/s while the writer sends a clean 30) trips no doctor — only a rate probe catches it; bounce the leg.
  • Thumbnail readers wedge on guest reset like any other reader — a frozen preview makes an operator distrust a live source and not cut to it.
  • Cloudflare 100 s edge timeout can 502 a long repair mid-flight — drive repairs against the local backend, not the public URL.
  • The status API's 500 ms micro-cache lies right after a cut — hold local state ~1.2 s after an action before trusting the poll.

17Standards & control plane (what we proved)

  • NMOS discovery works today. A stdlib IS-04 v1.3 Node presents every MXL flow as a standard Sender/Receiver — transport urn:x-nmos:transport:mxl, tags per AMWA BCP-007-03. Registered into an nmos-cpp registry, Bitfocus Buttons discovered the cloud facility — the first MXL facility in an NMOS registry that we know of.
  • A hardware panel is one Companion module away. A custom module drives a Stream Deck XL with real red/green tally over the switcher's REST. Confirmed on hardware.
  • The gap to a full facility: we built IS-04 (discovery). The next rungs are an IS-05 connection shim (so a controller can route us), then IS-07 tally and IS-08 audio. Each is independently demoable. That sequence turns "a demo" into "a facility."

18MXL vs NDI CPU: state the claim precisely

In an isolated five-minute 1080p30 ZoomISO comparison on the same older CPU-only host, native MXL averaged 165.74% CPU. Publishing the same source as NDI and returning it to the switcher's v210 MXL working format averaged 361.00% CPU across the publisher and bridge. The NDI route therefore used 2.18× as much CPU; native MXL reduced measured compute by about 54% in this stack.

A second controlled test replayed the same pre-generated v210 frames through both complete usable paths. At one and two independent readers, the NDI route used 1.78–2.14× as much median CPU; native MXL reduced compute by 43.9–53.4%. Every reader stayed around 30 fps with zero drops.

The result is intentionally bounded. It demonstrates the cost of an avoidable codec/network/conversion boundary between co-located software functions; it is not a universal verdict on every NDI implementation, GPU path, or cross-host workflow. The aggregate CSV, runnable harness, exact method, and limitations are published in the MXL vs NDI CPU deep-dive.
