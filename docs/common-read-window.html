When two MXL sources must not share an index

A switcher reading several MXL flows has to answer one deceptively simple question every frame: which grain do I read from each source? Running four live Zoom participants through an MXL-native switching core surfaced a subtle, deterministic failure in the obvious answer — and a fix that is more about when you need synchronization than about tolerating jitter. Everything below was measured, not guessed.

By Guy Cochran · Office Hours GlobalOct 2026 · four-input ZoomISO MXL, 1080p30 v210Companion: Field Findings

1The setup

The sources were four isolated Zoom participants, published as native video/v210 MXL flows by ZoomISO Cloud (Liminal's containerised Zoom media gateway). The consumer was a small, dependency-free switching core that creates stable Program and Preview flows once at startup and routes a source grain into each on every output frame boundary. Two independent media functions — a contribution gateway and a switcher — exchanging 10-bit uncompressed video over MXL shared memory. Exactly the Dynamic Media Facility picture, with real traffic rather than a diagram.

At first it looked clean, then under load the core began recording invalid output events. Direct probes on every MXL flow stayed healthy — full rate, no drops. CPU was abundant on both the producer and the consumer. And yet the switcher faulted. The interesting failures are the ones where every component is healthy and the composition is wrong.

2The grain ring is small, and that is the whole story

An MXL flow is a bounded ring of grains in shared memory — here, six grains per 1080p30 video flow. A reader selects a grain by index; the producer owns the slot just ahead of its write head, so the newest grain a reader may safely take is one behind the head, and the oldest still-valid grain is head − grain_count + 2. A six-grain ring therefore exposes a readable window of four discrete grains at any instant.

For a single source that is plenty. The subtlety appears when a switcher insists on reading two or more sources at one common index — the natural design if you imagine the switcher sampling "the world" at a single moment. The common readable window is the intersection of each source's window:

common_oldest = max(head_i − grain_count + 2)   over all sources i
common_newest = min(head_i)                     over all sources i
window_width  = common_newest − common_oldest + 1

If the sources are perfectly in step the window is the full five-wide. But independent producers are never perfectly in step.

3Why independent sources drift — and the four-frame cliff

Two Zoom participants are encoded independently. Zoom adapts each participant's bitrate and cadence to that person's network, so two MXL output flows advance their write heads at subtly different real-time phases. Call the gap between the furthest-ahead and furthest-behind head the source skew. With a six-grain ring the common window is simply:

window_width = (grain_count − 2) − skew + 1 = 5 − skew
  • skew 0 → width 5
  • skew 4 → width 1  (one usable grain left)
  • skew 5 → common_oldest > common_newest → the window disappears

So a six-grain ring affords only four frames of cross-source drift tolerance. Independent live sources routinely drift that far and briefly further. Each time skew touched five, the common window vanished for a frame or two, the switcher had no index it could read from both sources, and it recorded the moment as an invalid output. The fault was not jitter, not CPU, not a wedged source — it was a shared-index requirement meeting a small ring.

And critically, the ring depth was not ours to change: the ZoomISO build fixes its output ring at six grains, with no configuration, environment, argument, or sink property exposing it. Deepening the ring — which would have bought more tolerance for free — was off the table. The fix had to live in the switcher.

4The insight: a CUT needs no common index

The reflex fix is to make the switcher tolerate a transient empty window — wait a frame or two for the lagging source, hold the last valid picture, and only fault after the gap persists. That is correct and necessary, and we did it. But it treats the symptom. Step back and the deeper question is: why were we demanding a common index at all?

A common, single-instant sample of two sources is only required when you are combining them — a dissolve, a wipe, a picture-in-picture, a composite that mixes both pictures into one output at the same moment. A plain cut does none of that. On a cut, Program shows source A and Preview shows source B; the two outputs read two different sources that have nothing to do with each other. There is no reason Program's read of A must sit at the same index as Preview's read of B. They are unrelated timelines.

So the fix was conceptual, not brute force: let each output read its own source's latest-safe grain independently. Program reads A at A.head − margin; Preview reads B at B.head − margin; neither cares about the other's index. The common-window calculation is retained — but only as the primitive for a future transition path that genuinely samples two sources into one output. For the overwhelming majority of a show, which is cuts, the cross-source-drift problem simply does not exist, because there is no cross-source constraint to violate.

5The one hazard: a cut is a new timeline, not a regression

Going independent removes the shared-index constraint but introduces a new thing to get right. Once each output has its own input cursor, that cursor must be monotonic — a reader must never step backward into a stale grain. The naive guard is "reject any selected index below the last one." But a cut deliberately changes which source an output reads, and the new source's index counter is completely unrelated to the old one's. Two participants who joined a meeting minutes apart have index counters tens of thousands apart. Compare them and a cut looks like either a massive regression (reject the cut, or re-show a stale frame) or a massive skip (spurious alarm).

The rule that makes it correct:

  • The forward-only cursor is keyed by the (output, source) pair, never globally.
  • When an output's source changes — i.e. on a cut — its timeline resets: the new source starts at its own current safe index, and regression detection restarts fresh rather than comparing across the switch.
  • Within a single unchanged (output, source) timeline, recovery is forward-only: a candidate index below the saved floor is clamped if the floor is still in the ring, and if the floor has aged out of the ring the output holds its last valid picture rather than rewinding.

A cut is a legitimate discontinuity in an output's input timeline — a new timeline, not a rewind. Modelling it that way is what lets independent reads be both correct and monotonic.

6Transient vs sustained, and never spamming the fault

Two kinds of trouble remain, and they want different answers. Transient drift — a brief skew spike that recovers within a frame or two — is absorbed by the bounded wait and hold-last-valid on the transition path. Sustained drift — two sources settling at a steady offset and staying there — cannot be waited out, and with a fixed shallow ring there is no deeper buffer to fall back on. For that case the rule is to hold the last good picture and raise a single latched alarm, rather than emitting an invalid event every frame. A persistent fault should be visible once and actionable, not a flood that drowns the health signal. Independent per-output reads make sustained cross-source drift a non-event for cuts in the first place; the alarm covers the genuinely-degraded edge.

7How we knew it was alignment, not content

This failure is a perfect illustration of a lesson from operating MXL under load: "is it flowing" is not "is it good" — and here, the inverse bit us. Grain-rate and head-freshness probes stayed green through every window collapse, because the sources genuinely were producing fresh, changing grains the whole time. The plumbing was perfect; the composition dropped frames.

The decisive instrument was a content-uniqueness detector: hash a fixed centre slice of each grain and count distinct hashes per second. Through the collapses, every source kept reporting content changing at frame rate — no wedge, no freeze, no silence. That is what isolated the diagnosis: the sources were alive and the content was good, so the only thing left to blame was the switcher's cross-source alignment requirement. Content-uniqueness at the domain and byte-identical-frame (YDIF == 0) checking at the encoded output are the only honest liveness signals; rate and thumbnails will happily report health through this exact failure. (A fuller treatment of the honest-detector doctrine is in the field findings.)

8The measured result

With independent per-output read timelines on the cut path, the common window reserved for transitions, forward-only per-(output,source) recovery, and a latched sustained-unavailable alarm, the four-participant configuration ran clean:

  • A loaded 30-minute run of four ZoomISO MXL inputs plus stable Program and Preview — six flows total — held 30.00 fps with zero dropped grains across every probe (56,000+ grains per input).
  • Every failure counter stayed at zero: invalid, too-early, too-late, timeout, reader-reopen, synchronization errors, no-common-window, selected-input regression, and sustained-alarm events.
  • Observed common-window width sat at 4–5 grains and source skew at 0–1 grain in the steady state, with the independent path absorbing the excursions that previously faulted.
  • The switching core held the whole four-source cut/take path in under 80 MiB of RAM at a fraction of one CPU; the cost of software media lived in contribution and conform, not in the switch.

The health snapshot recorded clean timeline resets on each cut, zero selected-input regressions, and zero recovery clamps — the monotonicity rules held in practice, not just in the unit tests.

9The takeaway for anyone building on MXL

The portable lesson is not "tolerate jitter." It is a question to ask of any multi-source MXL consumer: when do your sources actually need to share an index? The answer is "only when you combine them into one output at one instant" — transitions and composites — and not for a cut, which is by far the common case. A shared-index design meeting a small, fixed grain ring will collapse under normal independent-source drift; an independent-index design makes that collapse structurally impossible for cuts, and confines synchronization to the moments that truly require it.

MXL's small rings are a feature — they are what make the shared-memory exchange cheap and low-latency. The discipline they demand is that consumers treat a common read index as a scarce, transition-only resource rather than a default. Build it that way from the start and four independent live sources cut cleanly, in under 80 MiB, on commodity hardware.
